= Customize and Extend
:navtitle: 5. Customize and Extend

== Modify Challenge Content

Challenge definitions live in YAML variable files.
You can customize them for any customer or partner engagement without modifying the playbook or roles.

=== Review the Challenge Structure

. In your Dev Spaces workspace, navigate to the deployment repository.
. Open `ansible-testing/vars/challenges.yml`.

Each challenge is defined as a YAML dictionary with these fields:

[source,yaml]
----
- name: "Challenge Name"
  description: >-
    Markdown-formatted description shown to participants.
  value: 50                  # Points awarded
  category: "At the Beach"  # Challenge category
  state: visible             # visible or hidden
  prerequisites:             # Challenges that must be completed first
    - "Previous Challenge"
  flags:
    - content: "{{ ctfd_flags.flag_name }}"  # Reference to vault-encrypted flag
      data: case_insensitive
  hints:
    - content: "Hint text shown to participants"
      cost: 5                # Point cost to reveal the hint
----

=== Add or Modify a Challenge

Let's modify an existing challenge to see how the process works.

. Open `ansible-testing/vars/challenges.yml` in your Dev Spaces editor.
. Find the "Ansible Docs" challenge in the *Warm Up* category.
. Change the `value` from `10` to `15`:
+
[source,yaml]
----
  - name: Ansible Docs
    description: What is the URL to find documentation about Ansible?
    value: 15  # Changed from 10
    category: Warm Up
    state: visible
----
+
. Optionally, add a new challenge to the Warm Up category:
+
[source,yaml]
----
  - name: "Red Hat Learning"
    description: >-
      What is the URL for Red Hat's free interactive learning platform
      where you can practice Ansible in a browser?
    value: 10
    category: Warm Up
    state: visible
    prerequisites:
      - Ansible Docs
    flags:
      - content: "{{ ctfd_flags.red_hat_learning }}"
        type: regex
        data: case_insensitive
    hints:
      - content: >-
          Search for "Red Hat interactive labs" or "Red Hat learning".
        cost: 2
----

[NOTE]
====
For new challenges that reference new flags, you must also add the corresponding flag value to `vars/flags.yml` (vault-encrypted).
Use `ansible-vault edit vars/flags.yml --vault-password-file .vault-password` to add new flag entries.
====

=== Configure Difficulty Tiers

Challenges are organized into difficulty tiers through their `category` and `value` fields. To adjust difficulty tiers for your audience:

. *Reassign categories* — Move a challenge between categories (e.g., from "Treasure Hunt" to "At the Beach") to change its perceived difficulty tier.
. *Adjust point values* — Higher values signal harder challenges. Use 5–15 for beginner, 25–50 for intermediate, and 75–100 for advanced.
. *Control prerequisites* — Add or remove `prerequisites` to gate advanced challenges behind easier ones, or open them for experienced audiences.
. *Toggle visibility* — Set `state: hidden` to remove challenges that don't fit the audience, without deleting them.

For advanced challenges, open the `ctfd_challenges_advanced` section at the bottom of the file. These verifier-based challenges represent the highest difficulty tier and require participants to write and run real automation against the managed node.

=== Review Advanced Challenges

The `ctfd_challenges_advanced` section defines challenges that use a *verifier service* — a sidecar container that SSH-es into the managed node to validate that the participant's playbook actually achieved the desired state.

Advanced challenges follow the same YAML structure but require participants to call a verification API endpoint after completing the task:

[source,bash,subs="attributes"]
----
curl -X POST https://{verifier_url}/validate \
  -H 'Content-Type: application/json' \
  -d '{"token": "YOUR_TOKEN", "challenge": "deploy-file"}'
----

== Re-Run the Idempotent Deployer

The deployment playbook is *idempotent* — re-running it updates only what has changed.

=== Apply CTFd Changes Only

To apply your challenge modifications without touching other infrastructure, use tags:

[source,bash]
----
cd ansible-testing
ansible-playbook deploy.yml --tags ctfd \
  --vault-password-file ../.vault-password
----

This scoped run:

* Loads cached credentials from the environment (no regeneration)
* Rebuilds and uploads only the CTFd challenge archives
* Leaves all other services untouched

=== Verify Your Changes

. Open your CTFd instance: {ctfd_url}
. Navigate to the challenges page.
. Confirm that the modified challenge now shows the updated point value.
. If you added a new challenge, confirm it appears in the correct category.

=== Verify Cached Credentials Were Preserved

After the re-deployment completes, verify that cached credentials were reused and not regenerated:

. Check the playbook output — look for tasks that say "loaded cached credentials" rather than "generating new credentials."
. Verify that `player.creds` was *not* regenerated by checking its modification timestamp:
+
[source,bash]
----
ls -la player.creds
----
+
The timestamp should be from the *original* deployment, not the current re-run.
. Confirm that existing player accounts still work by logging into CTFd with the same credentials from your handout.

=== Verify Runtime State Was Preserved

. Open CTFd and check the leaderboard — all player scores and flag submissions from Module 4 should still be intact.
. Verify that any previously submitted flags are still marked as solved.
. Confirm that leaderboard positions have not changed.

This demonstrates that runtime state (scores, submissions, leaderboard) is independent of the deployer — re-deploying does not reset participant progress.

=== Full Re-Deployment

Running the full playbook without tags re-executes all roles:

[source,bash]
----
ansible-playbook deploy.yml --vault-password-file ../.vault-password
----

The deployer *converges* to the desired state — only changes are applied. Existing infrastructure that already matches the desired state is left alone.

== State Coordination and Artifact Handoff

=== Deployer-Managed vs. Runtime State

Understanding what the deployer manages vs. what accumulates at runtime is critical for re-deployment decisions.

[cols="1,1,2",options="header"]
|===
| State Type | Examples | Re-deployment Impact

| *Deployer-managed*
| Challenge definitions, player accounts, CTFd configuration, Gitea repos
| Updated to match current variable files

| *Runtime*
| Scores, flag submissions, leaderboard positions, player progress
| *Unaffected* — lives in the CTFd database

| *Cached credentials*
| Player passwords, verification tokens (in environment state)
| Reused on re-runs; not regenerated
|===

This means you can *safely re-deploy* during or after an event to fix challenge content without resetting participant progress.

=== Fresh Environment Workflow — Artifact Handoff

This section demonstrates the full workflow for ordering a fresh RHDP environment and deploying from scratch using the provided playbook and roles.

==== Step 1: Order from RHDP

. Open the https://catalog.demo.redhat.com[Red Hat Demo Platform catalog].
. Search for *"Ansible Island Adventure"* or browse the catalog.
. Click *Order* and configure:
** *Number of users* — Set to the number of instructors/participants you expect.
** *Purpose* — Select the appropriate purpose (e.g., "Customer demo", "Partner workshop").
** *Duration* — Set to cover your event plus preparation time (typically 8–24 hours).
. Submit the order. Provisioning takes approximately 60 minutes.

==== Step 2: Receive Credentials

. Once provisioning completes, open the service details page in RHDP.
. You will receive:
** *Cluster API URL and admin credentials* — in the `rosa.creds` (or `.cnv.env`) file
** *Instructor usernames and passwords* — auto-generated and cached in `player.creds`
** *SSH keys* — for managed node access, stored in `keys/`
. No `player.creds` or `keys/` exist on a fresh environment — the deployer generates them automatically on the first run.

==== Step 3: Customize and Deploy

. Clone the deployment repository into your Dev Spaces workspace or local machine.
. Modify `vars/challenges.yml` to tailor challenges for the customer audience.
. If needed, edit `vars/flags.yml` to add or change flag values:
+
[source,bash]
----
ansible-vault edit vars/flags.yml --vault-password-file .vault-password
----
+
. Run the full deployer:
+
[source,bash]
----
cd ansible-testing
ansible-playbook deploy.yml --vault-password-file ../.vault-password
----
+
On a fresh environment (no cached `player.creds`), the deployer generates new credentials automatically.

==== Step 4: Generate and Distribute Handouts

. After deployment completes, the playbook publishes per-instructor handout data via `set_stats`.
. Use the handout data to create participant credential sheets with URLs and login information.
. Distribute handouts before or at the start of the event.

== Key Takeaways

* Challenge content is defined in YAML variables files and can be customized per engagement without modifying the playbook or roles.
* The deployer is idempotent: re-running it converges to the desired state — only changes are applied.
* Runtime state (scores, submissions) lives in the CTFd database and is independent of the deployer — re-deploying does not reset player progress.
* For customer events: order from RHDP → receive pre-deployed environment → customize challenges → distribute credentials → facilitate.
