= Customize and Extend
:navtitle: 5. Customize and Extend

== Modify Challenge Content

Challenge definitions live in YAML variable files.
You can customize them for any customer or partner engagement without modifying the playbook or roles.

=== Review the Challenge Structure

. Save your work in the survival-kit workspace, then switch to your `aia-instructor` workspace from Module 3. Post-deploy configuration allows both to run simultaneously with separate persistent storage. If you are still using older shared-storage workspaces, stop the survival-kit workspace before starting the instructor workspace. Use the instructor repository for event administration.
. In `/projects/aia-instructor`, open `roles/ctfd/vars/challenges.yml`.

Each challenge is defined as a YAML dictionary with these fields:

[source,yaml]
----
- name: "Challenge Name"
  description: >-
    Markdown-formatted description shown to participants.
  value: 50                  # Points awarded
  category: "At the Beach"  # Challenge category
  state: visible             # visible or hidden
  prerequisites:             # Challenges that must be completed first
    - "Previous Challenge"
  flags:
    - content: "{{ ctfd_flags.flag_name }}"  # Reference to vault-encrypted flag
      data: case_insensitive
  hints:
    - content: "Hint text shown to participants"
      cost: 5                # Point cost to reveal the hint
----

=== Add or Modify a Challenge

Let's modify an existing challenge to see how the process works.

. Open `roles/ctfd/vars/challenges.yml` in your Dev Spaces editor.
. Find the "Ansible Docs" challenge in the *Warm Up* category.
. Change the `value` from `10` to `15`:
+
[source,yaml]
----
  - name: Ansible Docs
    description: What is the URL to find documentation about Ansible?
    value: 15  # Changed from 10
    category: Warm Up
    state: visible
----
+
. Optionally, add a new challenge to the Warm Up category:
+
[source,yaml]
----
  - name: "Red Hat Learning"
    description: >-
      What is the URL for Red Hat's free interactive learning platform
      where you can practice Ansible in a browser?
    value: 10
    category: Warm Up
    state: visible
    prerequisites:
      - Ansible Docs
    flags:
      - content: "{{ ctfd_flags.red_hat_learning }}"
        type: regex
        data: case_insensitive
    hints:
      - content: >-
          Search for "Red Hat interactive labs" or "Red Hat learning".
        cost: 2
----

[NOTE]
====
For new challenges that reference new flags, you must also add the corresponding flag value to `roles/ctfd/vars/flags.yml` (vault-encrypted).
Use `ansible-vault edit roles/ctfd/vars/flags.yml --vault-password-file .vault-password` to add new flag entries.
====

=== Configure Difficulty Tiers

Challenges are organized into difficulty tiers through their `category` and `value` fields. To adjust difficulty tiers for your audience:

. *Reassign categories* — Move a challenge between categories (e.g., from "Treasure Hunt" to "At the Beach") to change its perceived difficulty tier.
. *Adjust point values* — Higher values signal harder challenges. Use 5–15 for beginner, 25–50 for intermediate, and 75–100 for advanced.
. *Control prerequisites* — Add or remove `prerequisites` to gate advanced challenges behind easier ones, or open them for experienced audiences.
. *Toggle visibility* — Set `state: hidden` to remove challenges that don't fit the audience, without deleting them.

For advanced challenges, open `roles/ctfd/vars/challenges_advanced.yml`, which defines `ctfd_challenges_advanced`. These verifier-based challenges represent the highest difficulty tier and require participants to write and run real automation against the managed node.

=== Review Advanced Challenges

The `ctfd_challenges_advanced` section defines challenges that use a *verifier service* — a sidecar container that SSH-es into the managed node to validate that the participant's playbook actually achieved the desired state.

Advanced challenges follow the same YAML structure but require participants to call a verification API endpoint after completing the task:

[source,bash,subs="attributes"]
----
curl -X POST https://{verifier_url}/validate \
  -H 'Content-Type: application/json' \
  -d '{"token": "YOUR_TOKEN", "challenge": "deploy-file"}'
----

== Apply Changes Deliberately

The toolkit has two different workflows. Reusing cached credentials is not a guarantee that player progress survives a deployment.

=== Update Challenge Content Through the API

Review `update-challenges.yml` in the instructor repository. It updates challenge definitions through the CTFd API rather than restoring a full database archive.

Before running it, the facilitator must resolve the deployment-input limitation described in Module 3: the current playbook still reads `rosa.creds` and derives a CTFd target from its defaults. Confirm that its target is *your intended CTFd instance*, that its administrator account is correct, and that you have compatible private inputs. Your existing personal OpenShift token does not override those pre-tasks.

When those inputs have been prepared and checked, run:

[source,bash]
----
cd /projects/aia-instructor
ansible-playbook update-challenges.yml
----

This API workflow updates existing challenges by name and retains their IDs. It also replaces flags and hints and deletes challenges absent from the definitions. Removing or renaming challenges can remove associated progress; changing points can change standings. Apply content changes before a customer event whenever possible.

=== Verify Your Changes

. Open your CTFd instance: {ctfd_url}
. Confirm that the edited challenge has the new point value.
. If you added a challenge, verify its category, prerequisites, hints, and accepted flag.
. Review existing solves and scores after an API update. Do not assume that deleting, renaming, or repricing a challenge leaves the leaderboard unchanged.

=== Full Deployment Resets Progress

[WARNING]
====
Running `deploy.yml` builds and imports a CTFd configuration archive. That restore resets the target board, including scores, submissions, and player progress. Stable passwords in `player.creds` do not preserve those records.
====

Use the full deployment exercise in Module 3 only with a facilitator-approved isolated target and compatible input files, before participants play. Do not run it during a customer event to apply a small content edit.

== State Coordination and Artifact Handoff

[cols="1,2,2",options="header"]
|===
| Operation | Intended Use | Effect on Progress
| `update-challenges.yml` | Update content through the API | Existing challenge IDs are retained; deletions, renames, and point changes can affect progress or scores
| `deploy.yml` | Full deployment and configuration archive import | Resets the target CTFd board and loses progress
| Cached `player.creds` | Reuse player passwords and tokens | Does not protect scores or submissions from an archive restore
|===

=== Fresh Environment Workflow — Artifact Handoff

This section demonstrates the full workflow for ordering a fresh RHDP environment and deploying from scratch using the provided playbook and roles.

==== Step 1: Order from RHDP

. Open the https://catalog.demo.redhat.com[Red Hat Demo Platform catalog].
. Search for *"Ansible Island Adventure"* or browse the catalog.
. Click *Order* and configure:
** *Number of users* — Set to the number of instructors/participants you expect.
** *Purpose* — Select the appropriate purpose (e.g., "Customer demo", "Partner workshop").
** *Duration* — Set to cover your event plus preparation time (typically 8–24 hours).
. Submit the order. Provisioning takes approximately 60 minutes.

==== Step 2: Receive Credentials

. Once provisioning completes, open the service details page in RHDP.
. You will receive:
** *Cluster API URL and access credentials* — in the service details; the legacy toolkit's `rosa.creds` input requires compatible fields supplied by the organizer
** *Participant service accounts and passwords* — in the handouts or service details; toolkit-created player credentials are cached in `player.creds`
. No `player.creds` exists on a fresh environment — the deployer generates it automatically on the first run. The managed node VM is provisioned separately by the student catalog item.

==== Step 3: Customize and Deploy

. Open your `aia-instructor` Gitea repository in Dev Spaces as in Module 3.
. Modify `roles/ctfd/vars/challenges.yml` to tailor challenges for the customer audience.
. If needed, edit `roles/ctfd/vars/flags.yml` to add or change flag values:
+
[source,bash]
----
ansible-vault edit roles/ctfd/vars/flags.yml --vault-password-file .vault-password
----
+
. Before a full deployment, have the facilitator verify an isolated target and compatible `rosa.creds` and `workshop.creds` inputs as described in Module 3. A full run resets the target CTFd board. Once that configuration is ready:
+
[source,bash]
----
cd /projects/aia-instructor
ansible-playbook deploy.yml
----
+
On a fresh environment (no cached `player.creds`), the deployer generates new credentials automatically.

==== Step 4: Generate and Distribute Handouts

. Review the root `generate-handouts.yml` and its documented workshop-access inputs with the facilitator.
. Use the generated `handouts/credentials.csv` and, where PDF-generation dependencies are available, `handouts/credential-handouts.pdf` to distribute participant URLs and login information.
. Distribute handouts before or at the start of the event.

== Key Takeaways

* Challenge content is defined in YAML variables files and can be customized per engagement without modifying the playbook or roles.
* Use the API update workflow for content changes, after verifying its target and inputs.
* Full archive deployment resets CTFd progress; cached player credentials do not protect scores or submissions.
* For customer events: order from RHDP → receive pre-deployed environment → customize challenges → distribute credentials → facilitate.
