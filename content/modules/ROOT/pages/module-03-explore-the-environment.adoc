== Deployment Artifacts Walkthrough

The environment was deployed using an Ansible playbook. Understanding these artifacts helps you troubleshoot and customize the platform.

=== Playbook Structure

The deployment playbook (`ansible-testing/deploy.yml`) uses a role-based structure to provision the full environment. The roles map to the logical deployment stages:

[source,text]
----
pre_tasks:
  ├── Load resource claim (.cnv.env)
  ├── Extract cluster credentials
  ├── Login to OpenShift as cluster-admin
  └── Build instructor list from player.creds

tasks (roles in execution order):
  ├── cluster_scale    → Scale worker nodes and install operators
  ├── players          → Create per-instructor namespaces and accounts
  ├── devspaces        → Deploy Red Hat OpenShift Dev Spaces
  ├── ctfd             → Deploy per-instructor CTFd instances
  ├── gitea            → Deploy shared Gitea and fork repos per instructor
  ├── aap              → Configure AAP organizations, inventories, credentials
  └── verifier         → Deploy per-instructor challenge verifier sidecars
----

The managed node VM is provisioned separately by the student catalog item — it is not part of this deployer. In the current implementation, these logical stages are organized into Ansible roles such as `cluster_setup`, `shared_gitea`, `instructor`, `configure_gitea`, `configure_ctfd`, and `configure_aap`. The role names may evolve, but the deployment stages remain the same.

=== Key Roles

[cols="1,3",options="header"]
|===
| Logical Stage | What It Does

| `cluster_scale`
| Scales worker nodes and installs cluster-wide operators (AAP 2.7, Dev Spaces)

| `players`
| Creates per-instructor namespaces, user accounts, and cached credentials (`player.creds`)

| `devspaces`
| Deploys Red Hat OpenShift Dev Spaces for browser-based IDE access

| `ctfd`
| Deploys per-instructor CTFd instances with MariaDB and Redis

| `gitea`
| Deploys shared Gitea instance and forks the `ansible-challenge` repository per instructor

| `aap`
| Configures per-instructor AAP organizations, inventories, and machine credentials

| `verifier`
| Deploys per-instructor challenge verification sidecars that validate automation results on managed nodes
|===

=== Stateful Files

Two key files coordinate deployment state and bridge the platform provisioning and the deployment automation:

[cols="1,3",options="header"]
|===
| File | Purpose

| `.cnv.env`
| ResourceClaim from RHDP — contains cluster API URL, admin credentials, apps domain, and user list. The platform provides this file automatically when the environment is provisioned.

| `player.creds`
| Cached per-instructor credentials — passwords and verification tokens generated on the first run and reused on subsequent runs. This cache-or-generate pattern ensures credential stability across re-deployments.
|===

The deployer loads `.cnv.env` to discover the cluster and build the instructor list. On the first run, it generates `player.creds`; on subsequent runs, it loads the cached version to avoid regenerating passwords. Flags are vault-encrypted in `vars/flags.yml` so they cannot be read from the repository.

NOTE: The managed node VM and its SSH access are provisioned separately by the student catalog item — they are not managed by the leaderboard deployer.

== RHDP Ordering and Provisioning Flow

For your own customer events, the workflow is:

. *Order from RHDP* — Search for "Ansible Island Adventure" in the https://catalog.demo.redhat.com[Red Hat Demo Platform catalog] and order the catalog item.
. *Wait for provisioning* — The platform provisions a shared OpenShift cluster and runs the deployment playbook automatically. This takes approximately 60 minutes.
. *Receive credentials* — RHDP provides cluster credentials and instructor handout data via the service details page.
. *Verify and customize* — Log in, verify all services, and customize challenges if needed (see Module 5).
. *Distribute handouts* — Share participant credentials and URLs before or at the start of the event.

[NOTE]
====
The environment arrives *fully deployed*. You do not need to run the deployment playbook for customer events — it runs automatically during provisioning.
====

== Key Takeaways

* The environment arrives fully deployed from RHDP — no manual installation is required for customer events.
* The deployment playbook and roles are provided as artifacts so facilitators understand what was deployed and can customize it.
* Stateful files (`.cnv.env`, `player.creds`) bridge the platform provisioning and the deployment automation.
* Ordering from RHDP is the supported path for running customer-facing events.
